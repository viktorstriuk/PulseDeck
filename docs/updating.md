# Канал обновлений и публикация

## Что реализовано

Это собственный updater на Node standard library, подписанный feed Ed25519 и
Go-движок обслуживания с пользовательским Electron-интерфейсом. **Не NSIS,
не `electron-builder`, не `electron-updater`, не `latest.yml`.** Такой выбор
позволяет выполнить требование полностью собственного окна и не вести параллельно
две несовместимые системы установки. Он также требует отдельной Windows-приёмки.

Источник задаётся в `app/updates/config.json`: `{owner,name}` и Ed25519 PUBLIC key.
Сейчас они пустые. Социальный профиль GitHub остаётся только ссылкой автора.
Не включённый источник не делает сетевых запросов проверки, не скачивает Setup
и не выдаёт ложное состояние «всё обновлено».

После настройки проверка выполняется спустя 15 секунд после старта, не чаще
одного раза в 12 часов; время и настройки сохраняются. Ошибки увеличивают паузу.
Ручная проверка ограничена 30 секундами, параллельные запросы объединяются.
Beta-канал выключен по умолчанию. Сначала отображается уведомление; закачка и
перезапуск происходят только после выбора пользователя. Приватные музыка,
пароли и тексты в update-запросы не включаются, но GitHub как сетевой сервис видит
IP/технический User-Agent. Сам музыкальный онлайн-поиск остаётся отдельной функцией.

## Подключение будущего репозитория

1. Создайте публичный репозиторий, перенесите обычные файлы исходников.
2. Создайте release environment с ручным подтверждением, защитите основную ветку
   и включите двухфакторную защиту аккаунта. Публикация Setup — доверенная операция.
3. **На своём доверенном компьютере**, вне дерева проекта, создайте ключ:

```sh
node tools/sign-release.js keygen --prefix /private/location/pulsedeck-update
node tools/sign-release.js configure --repo OWNER/REPOSITORY --public-key /private/location/pulsedeck-update.public.pem
```

`OWNER/REPOSITORY` — синтаксический пример, не адрес поставки. Команда `configure`
отвергает другой хост/неподдерживаемый ключ. Коммитится только PUBLIC key в JSON.
PRIVATE key хранится отдельно с резервной копией; при CI-публикации его PEM
передаётся в environment-scoped secret `UPDATE_PRIVATE_KEY_PEM`. Не кладите
закрытый ключ в приложение, ZIP исходников, историю Git или release artifacts.

4. Выпустите версию с настроенным источником. Установленным копиям 2.7.1 и
   ненастроенным версиям 2.8.0 / 2.8.1 нужно будет один раз получить её вручную: доверенный источник
   нельзя безопасно угадать или включить задним числом без обновления кода.
5. Прогоните две предварительные установленные сборки на Windows, затем публикуйте.

## Подготовка выпуска

Согласуйте `app/package.json`, `installer/ui/package.json`, `native/protocol.go` и
заметки `docs/releases/VERSION.{ru,en}.md`. Изменять бинарник под старым номером
нельзя: исправление означает новую версию. Стандартное имя —
`PulseDeck-Setup-VERSION.exe`, тег `vVERSION`.

```sh
python tools/build-release.py
python tools/package-source.py
node tools/sign-release.js application --private-key /private/location/pulsedeck-update.private.pem --notes-ru docs/releases/VERSION.ru.md --notes-en docs/releases/VERSION.en.md
```

Подписывайте **окончательный** EXE. При добавлении Authenticode сначала выполните
`signtool sign`/проверку подписи, затем генерируйте feed, размер, SHA-256. В этой
поставке сертификата нет; build.json честно отмечает `authenticode_signed:false`.

Стабильный выпуск создаёт два feed-файла, одинаковой версии, для обоих каналов:
`pulsedeck-update-stable.json` и `pulsedeck-update-beta.json`. Предварительный
выпуск создаёт только beta. В каждый GitHub Release загрузите соответствующий
EXE и feed. Иначе beta-пользователи не увидят завершённый стабильный выпуск.
Updater перебирает до 30 публичных релизов, пропускает drafts, stable не принимает
GitHub-prerelease и версии SemVer с суффиксом. Если длительно публиковать только
один тип assets, убедитесь, что нужный feed остаётся среди последних 30 релизов.

Формат envelope: `schema:1`, payload Base64 точных UTF-8 JSON bytes и подпись
Base64. Payload связывает product, kind, канал, OS/архитектуру, SemVer,
minimumVersion, переведённые заметки и file `{url,size,sha256}`. JSON не HTML.
URL приложения ограничен release/download настроенного репозитория. Приватный
GitHub-токен клиенту не требуется и не передаётся. TLS redirects ограничены
официальными asset-hosts; загрузка ограничена размером/тайм-аутом и завершается
через `.part` → fsync → rename только после проверки хеша.

При следующем запуске повторно проверяются подпись, версия, источник, обычный
файл без symlink, размер и SHA-256. Перед установкой runtime запрашивает разрешение
renderer: открытый редактор/диалог, конвертация, импорт, операции закрытой
библиотеки или обновление компонентов блокируют перезапуск. Настройки сохраняются,
файл ещё раз проверяется, затем запускается Setup и закрывается PulseDeck.
Неудачная установка перезапускает старую версию с флагом отмены повторного
авто-применения, чтобы не попасть в бесконечный цикл.

## FFmpeg/FFprobe и yt-dlp — независимо от приложения

Отсутствие репозитория PulseDeck блокирует только обновления **самого приложения**.
С 2.9.1 компоненты имеют отдельную кнопку «Проверить компоненты», собственное
состояние, доверенный IPC и фоновый таймер: через 12 секунд после старта, далее
каждые 12 часов, когда включена проверка компонентов. Выключение проверки обновлений
приложения не выключает проверку компонентов. Новые версии устанавливаются по
явному действию, не молча. Во время медиаопераций переключение версии блокируется.

Без собственного канала `app/updates/upstream-components.js` получает метаданные
из первичных источников: GitHub Releases проекта yt-dlp и API сборок Gyan для
FFmpeg. Один недоступный издатель не отменяет результат другого. Для yt-dlp
отклоняются draft/prerelease, проверяются точные имя/URL Windows EXE, размер и SHA-256.
Для FFmpeg сначала читается номер релиза, затем **версионный** URL ZIP и его
SHA-256, а не изменяемый `/latest` между двумя запросами. Понижение версии не
предлагается. Проверка и ремонт отсутствующих бинарников доступны при той же версии.

Модель доверия этого режима — HTTPS и SHA-256 от издателя, **не подпись PulseDeck**.
Хеш защищает целостность передачи, но сам по себе не исключает компрометацию
издателя. У приложения сохранены ограничения URL/redirect, размеров и тайм-аутов.
Транспорт приложения использует Electron `net.fetch`; системные proxy/PAC относятся
к нему. Go-bootstrap имеет отдельный HTTP-транспорт, полная проверка корпоративных
прокси/авторизации установщика остаётся в Windows-приёмке.

### Первичная установка

`app/updates/pins.json` содержит закреплённые дистрибутивы, проверенные по данным
издателей 26 сентября 2026: yt-dlp 2026.08.19 и Gyan FFmpeg 9.0.2. Setup читает pins
из уже проверенного payload и устанавливает обе группы **до commit кода приложения**.

Всё размещается в `<выбранная папка>/components`: загрузка `.part`, stage, полная
версия и `index.json`. SHA-256 проверяется до распаковки/запуска; ZIP-пути, ссылки,
дубликаты и размеры ограничены. FFmpeg и FFprobe устанавливаются вместе. Каждому
EXE выполняется ограниченный по времени пробный запуск с параметром версии, без
консоли. Есть официальный резервный URL Gyan на GitHub с тем же закреплённым хешем.

Полная уже проверенная такая же или более новая версия не скачивается заново.
Неполный набор восстанавливается. При недоступной сети, неправильном хеше или
ошибке probe нет ложного экрана успеха и код приложения не заменяется. Компонент,
который уже успешно установлен до ошибки следующего, может остаться в локальном
каталоге — это не транзакция всех групп и приложения как одного атомарного блока.

Приложение разрешает пути только внутри своей установки (`components` либо
совместимая локальная `tools`), проверяет реальные файлы, не ищет инструменты в
PATH и не использует внешние каталоги. См. [схему хранения](storage.md).
Успешные версии имеют receipt с хешами; перед возвратом к предыдущей версии
проверяется целостность. Неиспользованные внешние инструменты старых выпусков
не удаляются автоматически.

### Необязательный собственный подписанный каталог

Когда в `config.json` задан настоящий репозиторий и публичный ключ, сохраняется
режим одобренных Ed25519-каталогов вместо прямого discovery у издателей.
Для него подготовьте JSON с `channel`, монотонным положительным `sequence` и
`components`: `id` ffmpeg/ytdlp, version, minimumVersion, format zip/exe, license,
sourceURL исходного кода и file `{url,sha256,size}`. После проверки совместимости:

```sh
node tools/sign-release.js components --private-key /private/location/pulsedeck-update.private.pem --catalog /outside/repo/approved-components.json
```

Скрипт публикует `pulsedeck-components-stable.json` или beta. Для обоих каналов
нужны соответствующие подписанные копии. Sequence нельзя уменьшать или повторно
использовать для нового состава. Это отдельная модель одобрения; она не выдаётся
за свойство неподписанных upstream-метаданных.

## Защита и ограничения

Ed25519 защищает от замены feed/EXE на стороне хостинга без приватного ключа.
Не заменяет HTTPS, доверие к первому вручную установленному EXE, Authenticode,
антивирус или защиту компьютера автора. Компрометация приватного ключа требует
отзыва канала и вручную проверенного обновления доверенного ключа; автоматической
ротации ключей через неподписанный feed нет.

`.github/workflows/release.yml` собирает доверенную основную ветку, тестирует её,
подписывает feed и создаёт **draft**. Публикация после Windows-приёмки — действие
автора. В этом окружении workflow на GitHub не запускался: репозиторий и секрет
не заданы. Actions закреплены полными SHA, PR-проверки не получают release secret.
Рекомендуются immutable releases; повторная публикация той же версии запрещена
скриптом workflow. Бинарные/подписанные файлы публикуйте в Releases, не в Git.
